## Git 与 GitHub 的区别

两个名字经常一起出现，但它们是两回事：

- **Git**：跑在你电脑上的版本管理工具。它负责记录你项目的历史，全部存在本地；
- **GitHub**：一个托管网站，帮你把 Git 仓库放到网上——备份、分享、多人协作都靠它。

简单说：**Git 是工具，GitHub 是存放工具成果的地方**。没有 GitHub 也能用 Git（本地存档），但有了 GitHub，你的项目才有"云存档"和"给别人看"的渠道。

（顺带一提：GitHub 不是唯一的选择——GitLab、Codeberg、甚至自建服务都行。但本系列用 GitHub：教程、模板、自动发布全基于它。哦天哪，微软，我们还是得先赖着你……）

## 版本管理的基本对象

Git 的日常循环就三个动作：

```bash
git status    # 看看现在改了什么
git add .     # 把改动放进"暂存区"（准备提交）
git commit    # 提交：打一个存档点
```

三个概念对应三个地方：

- **工作区**：你正在编辑的文件（改动了但还没记录）；
- **暂存区**：`git add` 之后、`git commit` 之前的中间状态（"我确认这些改动要进存档"）；
- **历史**：`git commit` 之后，改动永久记入历史（`git log` 可以查看所有存档点）。

拿游戏存档类比就明白了：我们玩游戏，一般习惯是给**整个游戏**存档；但其实，你可以只给 Kris 存档、只给 Susie 存档——同理，`git add` 也能精确到文件：`git add 只改的那一个文件`，只把想提交的部分放进暂存区，不想提交的留在原地。发散一下你的小脑瓜，这能玩出非常多花样……哦哦，我们现在不是在设计游戏啊，那没事了。

初次接触会有点绕，但记住最小循环就行：**改代码 → `git add` → `git commit`**。存完一个档，心里就踏实一分。

来个完整的例子，从改完代码到存档：

```bash
git status
# 列出你改动的文件（红色 = 已修改、未暂存）

git add .
# 全部放进暂存区

git commit -m "feat: 添加狗的旋转动画"
# 打一个存档点

git log --oneline
# 历史的每一行：提交号 + 提交信息
```

`git log --oneline` 是看历史最常用的姿势——一行一个存档点，整个项目的成长线一目了然。

## 创建与接收项目

接收别人的项目用 `git clone`（第 01 集用过）：

```bash
git clone <仓库地址>
```

自己从零开始的项目用 `git init`——在项目目录里跑一下，它就变成 Git 仓库了。我们的教程项目走的是 clone 路线（use this template），所以你大概率用不到 `git init`，知道有这回事就行。

怎么判断一个项目是不是 Git 仓库？看它有没有 `.git` 文件夹——有，就是；没有，跑 `git init` 就有了。顺带说一句：thrash-machine 克隆下来就是完整的 Git 仓库（还带全部历史），你在上面做的每个 commit，都是接在这条历史线后面的——这就是"接收项目"的完整含义。

## 编写有用的提交记录

`git commit` 时会让你写提交信息——**这是给未来的自己看的**。写清楚"做了什么、为什么"：

```text
feat: 添加狗的攻击回合
fix: 修复骨头弹幕穿墙的问题
docs: 更新第 03 集博客正文
```

你可能想问：**为什么这里要 `feat` 开头啊？？** 因为这种"类型 + 描述"的标题叫**语义化标题**（conventional commits）——类型词本身就是信息：`feat` 新功能、`fix` 修 bug、`docs` 文档，一眼就知道这次提交是什么性质。更重要的是，下一集（EX04）的自动版本管理就靠它工作：机器人看到 `feat` 就升次版本、看到 `fix` 就升补丁。所以这格式不是给人看的规矩，是给机器看的协议——顺手也把"版本号为什么这么升"的语义化版本（SemVer）一起理解了。

现在养成习惯，后面就能顺顺利利。

看看我们 Dog Battle 仓库的真实历史：

```text
feat: 饶恕狗
feat: 狗睡觉
feat: 车生成骨头
fix: susie 应该在 gb 回合，只有自己受伤时，吐槽伤害
docs: 第 00 集博客正文
```

（另外，我知道你们可能有的人想说：啊啊你为什么用中文提交信息——适合自己的才是最好的。我暂且不需要和外国人合作，自己母语又是中文，提交信息写中文也基本不会炸，那就没有什么别的理由不写。你也一样：用什么语言，取决于和谁合作、给谁看。）

## 忽略不应提交的内容

有些东西**永远不该进历史**：构建产物（`.build/`、`dist/`）、编辑器状态（`.obsidian/` —— 哦这是我写文档的编辑器哈哈）、本地配置。用 `.gitignore` 文件把它们排除——thrash-machine 自带了一份，你可以打开看看里面写了什么。

## 分支与实验

分支（branch）是 Git 最强大的功能之一：**在分叉的路上做实验，不影响主线**。

```bash
git branch my-experiment   # 建分支
git checkout my-experiment # 切过去
```

想试个新玩法、不确定会不会成功？开个分支试。成功了，用 `git merge` 合并回主线，或者在 github 提个 pr 合并也一样；失败了，直接删掉分支，主线毫发无损。教程项目现在单人在做，可能用不上分支——但第 03 集说过"计划是地图，不是镣铐"，等你想试大改动时，分支就是那道保险。

## 与 GitHub 同步

本地存档是单机的，要备份和分享，得推送到 GitHub：

```bash
git push    # 把本地提交推送到 GitHub
git pull    # 把 GitHub 上的新提交拉下来
```

如果两边都改过同一块内容，`pull` 时可能遇到**冲突**——Git 会明确告诉你哪个文件冲突了，你打开它，把两边的内容合并成一份，再提交一次就好。第一次遇到别慌，冲突是协作的正常部分，不是灾难。

养成一个习惯：**push 之前先 pull**——先看看 GitHub 上有没有新的提交（可能是别人推的，也可能是你另一台电脑推的），拉下来合并，再推上去。顺序对了，冲突会少很多。

## Issue 与讨论

GitHub 的 **Issue** 是项目的问题追踪：bug、想法、待办，都可以开一个 Issue 记下来，有人跟进、有人讨论、解决后关闭。一个人开发也可以用它——把"想做的"和"做到的"分开，心里清楚得多。比如你想到"狗应该有睡觉动画"，开个 Issue 记下来，做完之后关掉它——每关一个 Issue，项目就前进一格。

## 协作与合并

多人合作时，标准的流程是：**分支 → 改动 → 提交 → 推送 → 提 Pull Request（PR）→ 别人审查 → 合并**。PR 是"我做好了，请你检查后合进去"的请求，GitHub 上看得见每一处改动，也方便讨论。流程拆开看：你推上去的分支 → GitHub 页面出现 "Compare & pull request" 按钮 → 点它，写清楚改了什么 → 别人 review（看代码、留评论）→ 通过 → 合并。合并之后，你的改动正式进了主线，分支可以删了。

下一集要讲的自动版本管理，就是靠"机器人开 PR"来工作的——到时会看到真实的 release PR 长什么样。

## 发布版本与回滚

Git 的 **标签（tag）** 给历史打上重要标记——通常是"这个版本可以发布了"：

```bash
git tag v0.1.0    # 给当前提交打上版本标签
```

第 01 集我们干过一件事：`git checkout v0.10.0`——把 Kristal 引擎切到某个版本。这就是 tag 的用法：**每个 tag 都是项目历史上的一个里程碑，随时可以回去**。

顺带解释个词：**CI**（Continuous Integration，持续集成）——把测试、构建、发布这些重复劳动，交给服务器（微软他们家的电脑上）自动完成。GitHub 的 CI 叫 GitHub Actions，你项目里 `.github/workflows/` 下的文件就是它的配置。

基于 thrash-machine 建的项目，CI 已经全部配好了：你只管往主线推代码，机器人会自动检测提交、自动开 release PR（下一集 EX04 会细讲整个过程）。不过有一个开关要记得打开：GitHub 仓库的 **Settings → Actions → General → Workflow permissions**，勾上"允许 GitHub Actions 创建并批准拉取请求"（Allow GitHub Actions to create and approve pull requests）——不然机器人开了 PR 也没权限合并，自动化等于没配。

回滚也一样：`git log --oneline` 找到想回去的提交号（那串黄色数字），然后：

```bash
git checkout <提交号> -- 文件名   # 恢复某个文件到那个版本
git checkout <提交号>             # 整个项目临时切到那个版本看看
```

注意：`git checkout <提交号>` 是"临时去看看"，看完记得切回主线（`git checkout main`）——别在"过去的版本"上继续写代码，那样写出来的提交会找不到家。存档的意义就在这里——永远有退路。

## Dog Battle 的实践流程

结合我们的项目，日常流程是：

1. 改代码（第 01 集的日常循环）；
2. `git status` 看一眼改了啥；
3. `git add .` + `git commit`（写清楚的提交信息）；
4. 阶段完成时 `git push` 到 GitHub——备份 + 记录进度。

关于 commit 的粒度，建议是：**一个功能（或一个修复）一个 commit**，而不是攒一大坨再存一次。存档越细，回滚越精准——改崩了想回到"改之前"，细的存档能精确到是哪一步引入的问题。

最后说说作者本人常用的开发方式，仅供参考：

- **小改动**：直接在 main 上改，push、push、push——改完就推，简单直接；
- **复杂内容**：开一个分支做，做完提 PR——自己给自己提也行。好处有三：改动过程有隔离，main 随时可运行；合作时别人能看到你怎么做的；合并时用**压缩合并（squash merge）**，分支上一堆零碎提交压成一个干净的提交，历史不脏（GitHub 合并 PR 时选 Squash and merge 就行）。

简单的事别上流程，复杂的事别裸奔——这就是我的版本。

把这个循环变成习惯，你的项目就永远有一条完整的时间线。这条时间线，就是下一集版本管理的原料。

## 结尾

Git 的核心就一句话：**改一点，存一档，说清楚**。剩下的（分支、PR、tag）都是这个核心的扩展。这篇先到这里，Git 的日常已经够用了——下一集（EX04）讲项目目录怎么组织，以及怎么用 Git 的历史 + 语义化版本号 + release-please，让版本号自动升、发布包自动出。
