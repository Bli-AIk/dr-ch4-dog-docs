# EX04：项目目录、素材管理与版本管理

这是一篇**番外**——上一集我们学会了 Git，这一集把项目的"家"收拾好：目录怎么组织、素材怎么放、版本号怎么管。

先记住一句话：**目录也是设计的一部分**。代码好不好看另说，文件放得乱，项目做到一半自己都找不到东西——这比代码难懂更致命。

## 为什么要管理项目结构

文件乱堆会带来四类问题：**找不到**（东西放哪了？）、**引用错**（同名文件改错一个？）、**冲突**（两个人改了同一个文件？）、**发布难**（打包时该带什么？）。这四个问题，全都可以用"从一开始就按规矩放"来避免。

## 区分项目内容

动手整理之前，先把项目里的东西分成三类：

- **源文件**：你的劳动成果——`scripts/`、`assets/`、`lang/`、`mod.json`、`mod.lua`。这些要进 Git、要发布；
- **可再生成**：构建产物——`dist/`、`.build/`、发布包。这些可以随时重新生成，**不该进 Git**（`.gitignore` 就是干这个的，上一集说过）；
- **个人配置**：`.obsidian/`（编辑器状态）、本地环境文件。只属于你，不该进仓库。

拿 thrash-machine 举例：`scripts/`、`assets/`、`lang/` 是源文件；`dist/` 和 `.build/` 是构建产物（第一次构建后才会出现，删了能重新生成）；`.obsidian/` 是编辑器状态——你看，三类东西在同一个项目里，一眼就能分出来。

分清楚这三类，后面所有决策都简单了：源文件精心维护，可再生成的随手删，个人配置不进历史。

## 组织 Kristal Mod 目录

Kristal 的目录结构是**约定好的**（第 02 集那棵目录树）：`scripts/battle/enemies/` 放敌人、`scripts/battle/waves/` 放回合、`assets/sprites/` 放图片……这不是随便分的，引擎就是按这些位置自动加载的。

所以规则只有一条：**新功能放它该放的地方**。实际用的时候，一张表就够：

| 想加的东西 | 放哪                           |
| ----- | ---------------------------- |
| 敌人    | `scripts/battle/enemies/`    |
| 弹幕回合  | `scripts/battle/waves/`      |
| 遭遇战   | `scripts/battle/encounters/` |
| 战斗演出  | `scripts/battle/cutscenes/`  |
| 地图    | `scripts/world/maps/`        |
| 角色    | `scripts/data/actors/`       |
| 物品    | `scripts/data/items/`        |
| 图片    | `assets/sprites/`            |
| 音效    | `assets/sounds/`             |
| 音乐    | `assets/music/`              |
| 文本    | `lang/`                      |

别为了"方便"自创目录——违背约定，引擎不认，别人也看不懂。除非你知道你自己在做什么。

## 管理图片、音频和字体

`assets/` 下每个类型都有自己的子目录（sprites/sounds/music/fonts），素材放对应目录即可。命名上记住动画的规矩：**每帧单独一张图，帧号附在名字末尾**（`idle_1.png`、`idle_2.png`……）——EX02 拆包时看过，这就是原作也在用的规范。

另外记住：代码里引用素材时，路径从类型子目录开始、**不带扩展名**（wiki 原话）——`assets/sprites/enemies/dog/idle_1.png` 在代码里写作 `enemies/dog/idle_1`。素材一旦改名，所有引用全断——所以动素材之前，先把名字想好。

## 管理语言与文本资源

对话、菜单文字、敌人信息——**文本不要散落在脚本里**，统一放 `lang/`（kristal-i18n 的 JSON 文件）。thrash-machine 里 `lang/` 的结构是这样的：`en.json` 和 `zh_hans.json` 放着所有要翻译的文本（key → 文本），`names.json` 放着角色名的各语言版本。想加一种语言？复制一份 JSON，翻译，然后在 `mod.json` 的 `kristalI18n` 配置里注册一下就行。

好处：想改一句话不用翻代码；想加语言，复制一份 JSON 翻译就行。我们的 Dog Battle 所有文本都在 `lang/` 里，代码里只有 `Game:loc("key")` 或者 `{key}` 这种引用。

## 统一命名和路径

两条小规矩，能省下大量"奇怪的问题"：

- **路径稳定**：素材路径一旦定下来，别动不动改——代码里到处引用着它（第 02 集说过，引用路径从类型子目录开始、不带扩展名）；
- **命名一致**：大小写、命名风格全项目统一。Kristal 的脚本 ID 是**区分大小写**的（第 02 集 wiki 原话），`Light/Pencil` 和 `light/pencil` 是两个东西——别在这种地方踩坑。

## 区分开发文件与发布文件

有些东西**只在开发时有用**：kristal-object-selector-plus（开发期摆物体）、terminal-cli（调试控制台）、debug 工具。thrash-machine 把这些组织在 `libraries/` 里，生产打包时**自动排除**——你不需要手动管，但要明白它们的定位：开发期的工具，不是游戏的一部分。看 `libraries/` 里的名字就知道哪些是这类的——它们进开发、不进发布，构建脚本自动处理。

## 素材来源与记录

EX02 教过素材怎么来、怎么判断能不能用，还给了那张来源记录表（素材/来源/许可/修改）。那张表记在哪里？**项目里放一份 `THIRD_PARTY.md`**——thrash-machine 自带了这个文件，就是给第三方素材做登记的。每加一份外部素材，顺手填一行，发布时它就是你的底气。

## 版本管理：SemVer 与 release-please

终于到重头戏了。版本号怎么定？别用 `final_v3_beta_test1225_真的最终版` 这种命名——用**语义化版本号（SemVer）**：

```text
v主版本.次版本.补丁
v0.1.0    → 第一个小版本
v0.2.0    → 加了新功能（次版本 +1）
v0.2.1    → 修了个 bug（补丁 +1）
```

规则很简单：**新功能升次版本，修 bug 升补丁，破坏性改动升主版本**。Kristal 引擎自己就是这么干的（v0.10.0 就是"第 10 个次版本"）。

两个小细节：第一，Kristal 系的版本号习惯带 `v` 前缀（`v0.10.0`），SemVer 本身是 `x.y.z`，带不带 v 看项目习惯——thrash-machine 带；第二，别小看"版本号"这件事——读者/玩家看到 `v0.2.0` 和 `v0.2.1` 就知道"加东西了还是修东西了"，你的更新日志也会因此自动写得清清楚楚。

还有 0.x 和 1.x 的一个关键区别：**主版本 0 表示"还没稳定"**——在 0.x 阶段，次版本升级可以随便包含破坏性改动，API 说变就变；只有到了 1.0.0，才算是"稳定承诺"：从此以后，次版本只能加功能、补丁只能修 bug，谁也别想破坏兼容性。Kristal 现在还是 0.10.0——还记得第 01 集说的"API 一直在变动"吗？这就是原因：它还没到 1.0。

手动改版本号容易忘、容易错。thrash-machine 内置的解决方案是 **release-please**——它是可以跑在 GitHub 上的一个机器人，它做的事是：

1. 盯着你的 main 分支的提交记录（上一集说的 conventional commit 格式，现在派上用场了）；
2. 发现 `feat:` 提交 → 自动把版本号升次版本；`fix:` 提交 → 升补丁；
3. 自动改好 `mod.json` 里的版本号、生成更新日志，开一个 **release PR**；
4. 你检查、合并这个 PR → 自动打上 `v0.2.0` 标签 → 触发构建流程，发布包自动出。

release-please 认识的提交类型是固定的，最常用这几个：

| 提交类型 | 含义 | 版本影响 |
| --- | --- | --- |
| `feat:` | 新功能 | 次版本 +1 |
| `fix:` | 修 bug | 补丁 +1 |
| `perf:` | 性能改进 | 补丁 +1 |
| `refactor:` | 重构（行为不变） | 无 |
| `feat!:` / `fix!:` | 破坏性改动（带感叹号） | 主版本 +1 |

写对类型，版本号自动升对——上一集让你养成 conventional commit 习惯的原因，现在看到回报了。

整个过程，你只需要写好提交信息、合并一个 PR。看看它在你项目里的真实配置——`mod.json` 里：

```json
"version": "v0.0.0", // x-release-please-version
```

那个 `// x-release-please-version` 注释就是标记：release-please 看到它，就知道"这里要自动改版本号"。再配合 `release-please-config.json`（告诉机器人怎么发版、更新日志放哪）和 `release.yml`（监听 `v*.*.*` 标签自动构建发布包）——整套自动化，模板里已经配好了。你 use this template 建项目的那一刻起，就有了这套能力，不需要从零配置。

## 发布前的目录检查

发布之前，最后过一遍项目目录：

- 源文件都在、可再生成的东西不在（`dist/`、`.build/` 别混进来）；
- `assets/` 里每份素材都有来源记录（EX02 的规矩）；
- `THIRD_PARTY.md` 登记完整；
- 开发期工具（kristal-object-selector-plus 之类）被正确排除；
- 版本号在 `mod.json` 里是"当前该有的样子"（release-please 会管，但看一眼不亏）。

检查清单里再加一条：`git status` 看一眼——如果构建产物、临时文件出现在列表里，说明 `.gitignore` 漏了东西，补上再提交。

## 结尾

目录是设计的延伸，素材和版本是项目的"长期资产"。把这三件事养成习惯，你的项目就不会随着体积变大而腐烂——第 10 集打包发布时，你会感谢现在收拾干净的自己。

另外说句题外话：目录和版本管理这些"看不见的功夫"，做的时候不觉得，但它是项目能不能活过三个月的分水岭。乱三个月，项目基本就烂在手里了；干净三个月，项目会自己长下去。
