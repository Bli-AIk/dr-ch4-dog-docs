# 第 02 集：如何使用 Kristal Wiki、API Reference 与示例项目

这是《从零做一个 Deltarune 同人游戏》系列的第 2 集。

上一集我们把开发环境搭好了。俗话说，师傅领进门，修行在个人——这一集依旧先不写代码，但可能是整个系列里性价比最高的一集：**学会自己查资料**。

先把核心观点说清楚：**Kristal 的 wiki 不是教科书，没有人需要从头到尾把它读完——它是字典，缺啥查啥**。硬啃文档是最低效的学习方式；带着问题来查，才是文档的正确打开方式。本集就用两个真实的问题示范怎么查：

- 在游戏里看到一个存档点——它是怎么来的？
- 想攻击敌人造不成伤害——怎么做到？

## 认识四种资料

动手之前，先分清手上有哪几类资料，它们各管一摊：

- **Wiki**（[kristal.cc/wiki](https://kristal.cc/wiki/)）：讲"**怎么做**"的教程集。事件怎么放、地图怎么画、文本怎么写，按主题组织成一篇篇指南。
- **API Reference**（[kristal.cc/api](https://kristal.cc/api/)）：讲"**这个功能是什么**"的字典。引擎里所有的类、方法、参数，从源码注释自动生成，按类型整理。
- **示例项目**：讲"**别人怎么写的**"的活标本。真实的目录结构、真实的调用方式，比任何抽象描述都直观。
- **别人的 mod**：讲"**这个效果是怎么实现的**"的标本，而且是最直接的那种。这里要先介绍一个 LÖVE 的本质：LÖVE 游戏本质上就是一堆 Lua 源码和素材打个包——`.love` 文件本身就是一个 zip，用解压软件就能打开；Windows 的 exe 版也一样，本质上就是"love 本体 + 你的游戏包"拼在一起。所以任何一个 LÖVE 游戏，只要作者没有刻意混淆，它几乎就是"开源的"——别人怎么实现的，拆开看就知道了。这也是为什么看别人的 mod 是极好的学习资料。

不过请记住一句话：**能看源代码，不代表可以不尊重别人的劳动成果**。开源不是免费，能看到代码不等于可以随便拿——学别人的思路、借鉴别人的做法，和直接抄素材、改个名当自己的发布，是完全不同的两回事。前者是每个开发者都走过的路，后者是另一个性质的问题（素材和版权的事，番外 EX02 会细讲）。

另外，对国内读者，Wiki 有我的中文翻译：[Shadow-ZH-Fork](https://bli-aik.github.io/Shadow-ZH-Fork/zh/wiki/)——文翻质量勉强说得过去（第 00 集提过），看得懂英文的话还是以官方为准。

## 阅读 Wiki：存档点是怎么来的

假设你在游戏里看到了那个星星——存档点。它是怎么来的？

第一步，把"现象"拆成"关键词"：存档点，英文 savepoint。然后想：它属于哪一类内容？它不是代码逻辑，而是 overworld 地图上的东西——所以去 Wiki 里找 **地图/事件** 相关的教程。

Wiki 的导航页（"项目创建"那一页）列着所有教程：设计地图、地图图层、使用事件、过场动画……"使用事件"（using-events）听起来就对。

进去之后你会看到一张大表：一堆事件的名字（可交互对象、脚本、宝箱、传送门……）。往下翻，找到**存档点（savepoint）**一节。读一下，答案就全了：

> 要创建这个 Event，请在 `objects` 图层上定义一个**点**或**单瓦片区域**，并将其命名为 `savepoint`。

就这么简单。存档点是 `Interactable` 的子类，还继承了一堆属性可以调：`marker`（重生标记——玩家死后从这里复活）、`simple`（简单版存档点——光世界常用的那种，没有招募和储物菜单）、`heals`（交互时是否回血，默认 true）……

注意，这一节开头其实还留了一句话："请先阅读设计地图，因为本教程会帮助你理解 Kristal 中的所有事件。"这就是教程的**前置提示**——顺着它走，基础就不会缺。查一个点，顺手把相关的线也看了，这是 wiki 的正确使用姿势。

再往下翻，这一节还带了一个**示例**——照着抄一遍，一个能用的存档点就出来了。这也是 wiki 教程的常态：先讲怎么做，再给你一个能跑的样板。别嫌"抄"丢人，第一遍抄，第二遍改，第三遍就是自己的了。

## 阅读 API Reference：怎么让攻击造不成伤害

第二个问题：想攻击敌人造不成伤害，怎么做？

这个问题 Wiki 教不了——它太具体了，属于"引擎内部怎么算"的层面。这种时候去 API Reference。

先想清楚关键对象：敌人被攻击时，引擎会计算伤害。算伤害的方法挂在哪个类上？我们可以去找敌人——`EnemyBattler`。然后在 API 站里找到 EnemyBattler，搜伤害相关的词，你会看到一个方法：

它的注释原文长这样（LuaDoc 格式——`---` 开头的是注释，`@param` 是参数说明）：

```lua
--- *(Override)* Gets the attack damage dealt to this enemy \
--- *By default, returns `damage` if it is a number greater than 0, otherwise using the attacking `battler` and `points` against this enemy's `defense` to calculate damage*
---@param damage    number
---@param battler   PartyBattler
---@param points    number          The points of the hit, based on closeness to the target box when attacking, maximum value is `150`
---@return number
function EnemyBattler:getAttackDamage(damage, battler, points)
```

翻译成人话：

> （你可以把这个方法重写 / 用你的方式换掉）获取这个敌人受到的攻击伤害。
> 默认的行为：如果 `damage` 大于 0，就原样返回它；否则用 `battler` （攻击者）和 `points` （命中准确度）来算，再减去这个敌人的 `defense`（防御力）。
> 
> 参数：`damage` 是数字类型（number），`battler` 是攻击者类型（PartyBattler），`points` 是数字类型——按攻击时准星贴近目标框的程度计算，最高 150。
> 
> 返回：伤害值。

注释会告诉你三件事：这是一个 **Override**（可重写）方法；默认逻辑是"如果 `damage` 大于 0 就原样返回，否则用攻击力和命中点数算伤害，再减去防御"；参数分别是伤害值、攻击者、命中点数（最高 150）。

到这里，答案已经出来了：**重写这个方法，让它永远返回 0**。比如我们的 Dog Battle 里，神烦狗就是这么做的：

```lua
-- The dog dodges every attack instead of taking damage.
function Dog:getAttackDamage(damage, battler, points)
    return 0
end
```

所以那条狗为什么砍不动？因为这一行。你看，一个"想攻击敌人造不成伤害"的需求，走到最后就是重写一个方法、返回一个 0。

顺带一提，API Reference 的内容其实就长在源码的注释里（LuaDoc，`---@param` 那种格式）——官方 API 站是从源码注释自动生成的。所以如果你手边有引擎源码（第 01 集克隆过），直接翻 `src/engine/game/battle/enemybattler.lua`，能看到一模一样的信息，而且还能顺带看它旁边的其他方法。文档会骗人（可能过时/没有维护。但kristal文档会自动更新——但也可能和你的引擎版本不一致），源码不会。

## 观察示例项目：thrash-machine

第三种资料：示例项目。你不是已经有一个了吗？——thrash-machine（第 01 集建的）。你甚至已经和它的训练人偶打过一架了（往右走进 room2 那个），现在来看看它背后长什么样。

打开它的目录，你会发现里面的组织方式和 Wiki 讲的完全对应——一颗标准的 Kristal 项目目录树长这样：

```text
thrash-machine/
├── mod.json            # 项目配置（ID、章节、队伍、物品……）
├── mod.lua             # 项目入口
├── assets/             # 素材
│   ├── sprites/        #   图片（精灵）
│   ├── sounds/         #   音效
│   ├── music/          #   音乐
│   └── fonts/          #   字体
├── scripts/
│   ├── battle/         # 战斗
│   │   ├── enemies/    #   敌人
│   │   ├── encounters/ #   遭遇战
│   │   ├── waves/      #   弹幕回合
│   │   ├── cutscenes/  #   战斗演出
│   │   └── bullets/    #   弹幕
│   ├── data/           # 数据
│   │   └── actors/     #   角色（物品、法术等也在这层）
│   ├── objects/        # 自定义对象
│   └── world/          # 世界
│       ├── maps/       #   地图
│       └── cutscenes/  #   过场
├── lang/               # 本地化文本（kristal-i18n）
└── libraries/          # 库
```

（这个模板里的 `lang/` 是 kristal-i18n 加的，原版引擎创建的项目没有；`data/` 下按 wiki 的约定还可以放 `items`、`party`、`spells` 等目录，模板里暂时没有而已。）

随便打开一个文件看真实写法——比如 `scripts/battle/enemies/dummy.lua`（训练人偶）：它定义了一个 `Class(EnemyBattler)` 的类，`init` 里设置血量、攻击力、ACT 选项，`onAct` 里写各个 ACT 的效果。你在 Wiki 上学到的"敌人怎么写"，在这里能看到完整的真实形态。

观察示例项目有个要点：**不要只看某一个局部，先看目录再看到文件**。目录告诉你是"什么"，文件告诉你是"怎么写的"。把两者对应起来，你就理解了这个项目的骨架——之后自己加内容，就知道该往哪放。

## 拆一个别人的 mod

光看 Wiki 和 API 是纸上谈兵，最快的成长是拆一个真的 mod。实操就三步：

**第一步：拿到源码。** `.love` 文件本身就是 zip，用 7-Zip 之类的解压软件直接就能打开；Windows 的 exe 版也一样能拆——它本质上是"love 本体 + 你的游戏包"拼在一起，解压工具能把它分开。拆开之后，你会看到和 thrash-machine 一模一样的结构：`mod.json`、`mod.lua`、`scripts/`、`assets/`……

**第二步：从配置读起。** 先看 `mod.json`——项目 ID、起始地图、队伍、物品，甚至直接进哪个战斗（`encounter` 字段）。这份配置就是整个项目的"目录页"，看完它，你对这个游戏是什么结构就心里有数了。

**第三步：顺着现象找实现。** 想学它的某个效果？把现象拆成关键词（还是老办法），然后按目录定位：战斗相关的进 `scripts/battle/`，地图相关的进 `scripts/world/`，文本相关的找 `lang/` 或 `assets/`……找到对应的文件，读它怎么写的——和上一节看 thrash-machine 一个套路，只是这次是别人的真实作品。

拆的时候有两点要注意：

- **看到不认识的调用别慌**：很多 mod 用着别人写的库（`libraries/` 目录），不认识的函数先看它来自哪个库——库是别人的成果，用之前看许可（第 00 集说过，模组是可以带库的）。
- **拆开是学习，不是复制**：把"它的实现"变成"你的理解"，而不是把文件原样搬进你的项目。素材更是如此（番外 EX02 会细讲）。

如果作者做了混淆、或把 Lua 编译成了字节码，拆开也读不了——这种就别费劲了，尊重人家的选择。

当然，也有的开发者喜欢把自己做的个人项目整个开源——那就更省事了，连拆都不用拆，直接 `git clone` 下来就能读。比如我本人的另一个项目 krisis knightmare，代码就是开源的（虽然写得一坨就是了，草）。

但有一件事比拆包更优先：**看许可证**。能拆开、能 clone，都不代表你可以随便用——每个项目都有自己的许可条款，尤其是发布在 GameBanana 这类平台的游戏 / 库，页面和包里通常都带着许可证信息，动手之前先看一眼。常见的几种，认个脸熟就行：

- **MIT / Apache-2.0**：最宽松的一档，随便用、改、甚至商用，只要保留版权声明。很多库和模板都是这类（比如我们的 thrash-machine 就是 MIT/Apache-2.0 双许可）。
- **GPL 家族**：
  - **GPL**："传染性"许可——用了它的代码，你的项目也得用 GPL 开源。想保留自己代码的话，遇到 GPL 要慎重。
  - **AGPL**：GPL 的网络强化版——就算你不分发、只把游戏挂在网上当服务提供，也得开源。遇到它比 GPL 更要慎重。
  - **LGPL**：GPL 的"库友好"变体，专为库设计——闭源程序也可以链接使用它（只要不改库本身）。用库时看到 LGPL，会比看到 GPL 舒服一档。
- **CC 系列**：主要给内容（素材、文本、音乐）用的。CC-BY 署名就行；CC-BY-SA 还要相同方式共享；CC-BY-NC 不能商用；最宽松的 CC0 约等于放弃版权。
- **什么都没标**：默认等于"保留所有权利"——没有许可证，就不存在"允许"。

这套规则对 **library（库）同样适用**——用别人的库之前，先看它的许可证，规则一模一样（thrash-machine 的 `libraries/` 里每个子模块都有自己的许可文件，你可以现在就翻翻看）。

一句话总结：**能看 ≠ 能用，能用 ≠ 能商用**。看许可证花不了两分钟，但能省下后面一大堆麻烦。

最后多说一句：**同人游戏的商用本身也不应当**。Deltarune 的世界是 Toby Fox 的，同人作品免费分享是社区常态，拿原作 IP 做游戏卖钱就是另一回事了——这一点和许可证无关，是更基本的尊重。

## 把需求转换成查找路径

两个例子走完，回头看通用的方法。一个"想实现的效果"要变成"查到的资料"，中间就三步：

1. **拆关键词**：效果 → 名词。存档点 → savepoint；攻击造不成伤害 → damage。
2. **判断类型**：它是"怎么做"（教程类）还是"是什么"（功能类）还是"别人怎么写"（示例类）？
3. **选对入口**：教程类 → Wiki 对应主题页；功能类 → API Reference 找对象；写法类 → 示例项目找同类文件。

来点实战预演——把第 00 集"项目事实"里的需求映射一下：

- "想给敌人加一个讲笑话的 ACT" → Wiki 的敌人/遭遇战教程 + thrash-machine 的 dummy.lua 看 ACT 写法；
- "想做一个会移动的弹幕" → Wiki 的弹幕教程（wavemaking）+ 示例项目的 `waves/` 目录；
- "想让敌人被攻击时有特殊反应" → API Reference 的 EnemyBattler（你会发现 `onHurt` 之类一堆可重写的方法）；
- "想让游戏启动后直接进入战斗" → Wiki 的创建项目教程（mod.json 那一节，`encounter` 字段）——我们的 Dog Battle 就是这么配的。

你会发现大多数需求，走这三步都能落到某个具体页面或文件上。

## 记录和验证结果

查到了，别急着信——**回项目里验证**。改一行代码，`Ctrl+R` 热重载（第 01 集教的），看行为是否符合文档说的。验证的方式分两种：简单的小改动，直接跑起来看行为对不对；涉及数值的，可以开调试控制台（第 00 集提过的反引号控制台），输个 `=变量名` 直接看实际值。行为和值都对上了，这条资料才算真正到手——文档可能过时、可能省略细节，验证过的东西才是你的。

另外养个习惯：把查到的来源和结论记下来（一个笔记文件、甚至就是注释）。同一个问题，下次就不用从头再查一遍——你会发现"查资料"这件事，查过一次的问题会越来越少。

## 不懂就问，但你得先研究

这套查资料的方法走到头，总有几个问题是怎么都查不到的。这时候，该问人了——Kristal 的社区（Discord、国内群）都很乐意帮忙。

但先说个梗：网上流传过一张"如何正确提问"的梗图，问问题的人得到的回复永远只有一句"你研究过了吗？"——讽刺的正是那些不查资料、张嘴就问的人。梗归梗，它说的道理是真的：**提问之前，先证明你自己研究过**。

带着什么来问，决定了你能得到什么答案。一个好问题长这样：

- **版本信息**：引擎版本（v0.10.0？）、系统（Windows？Linux？）；
- **复现步骤**：做了什么，然后发生了什么——"我改了 waves/basic.lua 里的 X，按 Ctrl+R 之后报错了"；
- **错误信息**：报错全文，别只截一半图；
- **尝试过什么**：查过 wiki 哪一页、试过哪个方案、结果如何。

"我试了 X，报错 Y，我怀疑是 Z，请问怎么看？"——这种问题，谁看了都愿意答。而"为什么我的游戏打不开？"这种，没人答得上来，因为你自己都没研究过。

答完之后，记得把答案也记下来——查资料的最后一环是"记录"，问人也一样。

最后，始终记得一件事：**别人回复你是情分，不回复是本分**。社区的开发者们没有义务替你解决问题——他们愿意花时间，是善意；没人理你，也很正常。带着感恩提问，带着礼貌道谢，这个社区才会一直有人愿意回答。

## 结尾

这一集的核心就一句话：**缺啥查啥，查完验证，验证完记录**。文档是工具，不是门槛。
